Start hereWhat this page is

TinyTracer is a small chip that draws a picture of a 3D scene by ray tracing. The University of Waterloo ASIC Design Team designs it, and it is made through Tiny Tapeout, a service that puts small designs on a shared chip (docs introduction.md).

Ray tracing makes each pixel by following a straight line of light, a ray, from the camera through the pixel into the scene. The chip finds the first object that the ray hits. From the hit point it sends the ray on in a new direction (a bounce). This repeats until the ray reaches the sky, reaches a glowing object, or has bounced 8 times. The colours met on the way give the colour of the ray. Each pixel is the average of several rays (samples) that start at slightly different points in the pixel, which smooths edges and noise.

A laptop sends the scene to the chip over a serial link (UART). The chip sends back one finished pixel at a time; it works on one pixel at a time because it must be small.

How the page is ordered. It goes from the whole system down to single operations. Level 0 is the laptop and the chip. Each next level opens the boxes of the level above. Level 5 shows every calculation of one straight piece of a ray path, with real numbers (sections 5a–5h). Level 6 shows the maths units. Timing A, B and C then give the time for one frame, one sample and one operation.

Sources. “The docs” are the design documents in the docs folder of the TinyTracer repository; a file name such as cordic.md is a file there. Blocks and rows marked “added” are in this design but not in the docs. “The sim” is the C++ model sim/tinytracer_sim.cpp in the same repository. It renders the demo scene with the same 16-bit maths as the chip and counts every operation. Every measured number on this page comes from it. The Sources table at the end lists what comes from the docs, what was decided for this design, what the sim measured, and what is assumed.

Before the diagramsNumber formats

The chip has no floating point. A fixed-point number is a 16-bit integer, the raw value, read with a fixed binary point. Qm.n means m bits before the binary point (sign included) and n bits after it, so the value is raw ÷ 2^n. POS (position format, Q9.7): value = raw ÷ 128. DIR (direction format, Q2.14): value = raw ÷ 16,384. A multiply of two 16-bit numbers gives a 32-bit product; “shift n” below means the product is shifted right by n bits, with rounding, to give 16 bits.

Level 0The whole system

The laptop sends the scene once, then one render command; the chip returns one pixel at a time.

Level 1Blocks on the chip

The RTU decides the ray tracing steps. It does no maths itself. For each calculation it sends a macro-op to the Decode Unit. The Decode Unit runs micro-ops on the ALU, the multiplier and the CORDIC unit, and it returns three 16-bit numbers.

Request: the docs’ 101 bits (5-bit opcode, six 16-bit numbers) plus 1 format bit for the multiply shift: 0 = shift 7, 1 = shift 14 (Number formats). Colour multiplies also need shifts 8 and 10, which one bit cannot select; this is still open (Review). K is applied in the RTU and never reaches Decode. Micro-op: 13 bits plus the same format bit.

What the SRAM holds

Level 2Inside the RTU

The Controller runs the pixel, sample and bounce loops and starts one sub-block at a time. The Intersection Unit runs the bounding-volume and object loops. Each sub-block sends its own macro-ops and reads its own flags. The RTU builds each request field from one of six sources (Operand select), shifts it by K where needed, and holds it in the request register. A result goes into the next request, into the ray state, or back to the sub-block as a flag.

Level 4One segment

A skipped bounding volume costs no object reads: w0 is read only if the BV is reached. Colour words are read only for the closest hit. The ground is tested only if no object was hit. This gives the right answer as long as every object sits at z ≥ 0: along a ray that goes down, an object point at z ≥ 0 always comes before the ground at z = 0.

5a · Camera ray

DoesMakes the first segment of a sample: start O and length-1 direction D through one point of one pixel.
Block · whenRay Generator · every sample (up to 32 per pixel)
Inpixel x, y (9 bits each); 12 LFSR bits; F, R, U, camera z (header registers)
OutO = (0, 0, camera z), D; attenuation = 255; bounce = 0

A screen of 512 × 512 pixels sits in front of the camera. F points to its centre, R from the centre to the right edge, U from the centre to the top edge. A screen point is F + a × R + b × U, with a from −1 (left) to +1 (right) and b from +1 (top) to −1 (bottom). D points through it.

The laptop computes F, R and U once, so the chip needs no sine or cosine here. 6 random bits of jitter move each sample to a different point inside the pixel; the average smooths edges.

The chip makes a and b by placing bits; there is no adder. In DIR, 1.0 is 16,384 steps. The screen is 2.0 wide (a = −1 … +1) and 512 pixels across, so one pixel is 2 ÷ 512 × 16,384 = 64 steps, and a × 16,384 = (x − 256) × 64 + jitter. x − 256 is x with bit 8 inverted, read as a signed 9-bit number: x = 302 = 1 0010 1110 → 0 0010 1110 = +46. The top row must give b = +1, so b uses 255 − y, which is y with bits 7–0 inverted: y = 248 → 7.

The distances in the tests (5c–5e) are true distances only if |D| = 1, and the mirror and glass formulas (5g) need |D| = |n| = 1.

The RTU first shifts all 3 parts by the same amount, so that the largest part is 0.5 … 1 when read as DIR. The shift also turns a POS arrow into DIR. The length is then 0.5 … 1.73 (√3), so 1 ÷ length is 0.58 … 2. DIR holds up to 1.99994, so a 2 clamps; the result is then half a step short, which is too small to matter.

Then the RTU sends one macro-op, M_NORM. It uses three kinds of micro-op: MAG(a, b) = √(a² + b²), the length of a 2-part arrow; RECP(a) = 1 ÷ a, the reciprocal; and MUL, a multiply. m = MAG(x, y), length = MAG(m, z), inv = RECP(length), then x × inv, y × inv and z × inv. If all parts are 0, the leading-one finder finds no 1; the matte bounce uses this (5g).

5c · Bounding volume test

DoesDecides if the ray can touch a bounding volume (BV). If not, every object inside it is skipped.
Block · whenIntersection Unit · every segment, once per BV (4 in the demo scene, up to 16)
In · outO, D, centre C, radius r (BV words w1–w4) · reach (then read w0, test the objects) or skip

The laptop puts a sphere around a few nearby objects: a bounding volume (BV). One BV test (at most 76 cycles) can skip every object inside it; in the demo scene 3.38 of 4 BVs are skipped per segment. BV i sits at address 17 + 5 × i (memory map, Level 1).

to_centre = C − O is the arrow from the ray start to the centre. along = to_centre · D is the distance along the ray to P, the ray point closest to C (this needs |D| = 1). P = O + along × D, so offset = P − C = along × D − (C − O) = along × D − to_centre. |offset| is the closest distance between the ray and C.

1. |to_centre| < r: the ray starts inside → reach. Every bounce starts inside its own BV.
2. along < 0: the centre is behind the start, and the start is outside. Moving along the ray only takes the ray farther from C → skip.
3. |offset| < r → reach, else skip.
Squares are compared after the K shift (5d explains K). A square above 256 clamps to 255.99. The compare still gives the right answer, because r_s² is at most 256.

Same to_centre, along and offset as 5c. |offset| ≥ r → miss. Otherwise the ray crosses the sphere half a chord before P and half a chord after P: half = √(r² − |offset|²). The entry point is at t = along − half. If t ≤ 0.0156 (2 POS steps), the entry point is not in front of the start. Then either the start is inside the sphere (glass), or the whole sphere is behind the start. The test tries the exit point, t = along + half. If that is also ≤ 0.0156, the sphere is behind the start: miss.

K, the size shift. The test squares two numbers, |offset|² and r². POS stops at 256, so a sphere with r = 20 would give r² = 400 and clamp. A small sphere has the opposite problem: r = 1.5 gives r² = 2.25, and POS has only 7 bits after the point, so few correct bits are left. So before squaring, the RTU scales the sphere by a power of 2 so that its radius is 8 up to 16; then r² is 64 up to 256. A power-of-2 scale is a shift, so it costs 0 cycles. K is that shift: K > 0 shifts right (÷ 2^K), K < 0 shifts left (× 2^−K).

To pick K, the leading-one finder looks at the radius as a raw number (raw = r × 128) and finds its highest 1 bit. Every radius from 8 up to 16 has raw 1,024 … 2,047, whose highest 1 is bit 10.

K = (highest 1 bit of the raw radius) − 10. After the shift, the radius is 8 up to 16.

5e · Triangle test

DoesFinds the distance t where the ray crosses one triangle.
Block · whenIntersection Unit · every triangle of a reached BV (0.61 per segment)

Points of the triangle’s plane are v0 + α × e1 + β × e2. α and β are the triangle coordinates of the point (many books call them u and v; on this page u and v are the request fields). A point is inside the triangle when α ≥ 0, β ≥ 0 and α + β ≤ 1. The test (Möller–Trumbore, docs) finds α and β where the ray crosses the plane, and it stops at the first failed check.

K for a triangle. The test multiplies edge parts with each other and with slid (defined in stage 1 below). Each result adds two or three such products and must stay below 256. So the RTU scales the triangle by a power of 2 until its largest edge part is 4 up to 8 (raw 512 … 1,023, highest 1 bit = 9). An edge is then at most 8 × √3 = 13.9 long.

K = (highest 1 bit of the largest raw edge part) − 9. After the shift, the largest edge part is 4 up to 8.

The four stages.
Stage 1. to_corner = v0 − O and along = to_corner · D, as in 5c. slid = along × D − to_corner is the arrow from v0 to the ray point closest to v0 (the ray start, slid along the ray). After the K shift, every point of the triangle is within 13.9 of v0. If the ray passes more than 15 from v0 (|slid_s|² > 225), it misses. 15 is a little more than 13.9, so rounding cannot reject a real hit. The later stages use the small slid_s instead of O − v0, which keeps their products small.
Stage 2. P = D × e2, det = e1 · P and α_top = slid · P. det (short for determinant) is the number that α and β are divided by: α = α_top ÷ det and β = β_top ÷ det. det = 0 means the ray is parallel to the plane. det < 0 means the ray meets the back side: the RTU flips the signs of det and α_top (flip bit = 1), and later of β_top.
Stage 3. Q = slid × e1 and β_top = D · Q.
Stages 2 and 3 check 0 ≤ α_top, 0 ≤ β_top and α_top + β_top ≤ det without dividing. Stage 4 divides and finds t = along + α (e1 · D) + β (e2 · D). This follows from O + t × D = v0 + α × e1 + β × e2: the dot product of both sides with D (|D| = 1) gives t = (v0 − O) · D + α (e1 · D) + β (e2 · D), and (v0 − O) · D = along.
Sizes: |det| ≤ 13.9 × 13.9 = (8√3)² = 192, and α_top, β_top ≤ 15 × 13.9 = 208. Both stay below 256.

Glass: glass bends light. The index of refraction (IOR) is 1.5 for glass and 1.0 for air. η is the ratio of the two indices: 1 ÷ 1.5 = 0.667 going in, 1.5 going out. cos θ = −(D · n) is the cosine of the angle between the incoming ray and n. k = 1 − η²(1 − cos²θ). If k < 0, no bent ray exists (total internal reflection), so the ray reflects. Otherwise the ray reflects with the chance share = 0.04 + 0.96 (1 − cos θ)⁵ (Schlick’s formula: 0.04 = ((1.5 − 1) ÷ (1.5 + 1))² is the head-on reflection of glass, and 0.96 = 1 − 0.04), picked with 8 random bits, and bends in the other cases.

Random arrow r. A height z (8 bits) and a heading φ = w × 90° (8 bits), both picked evenly, give every direction the same chance; 2 sign bits pick the quarter turn. ρ = √(1 − z²) is the radius of the circle at height z on a radius-1 sphere. r = (±ρ cos φ, ±ρ sin φ, z), with sin φ = cos(φ − 90°). φ in 0 … 90° keeps both M_COS inputs within the CORDIC range (±99.8°).

What M_COS does. It takes an angle in radians as a DIR number (0.920 means 0.920 rad = 52.7°) and returns the x of the point at that angle on a circle of radius 1: cos 52.7° = 0.605. The y of that point is sin φ = 0.796. The matte bounce is the only user of cos; the camera needs none, because the laptop computes F, R and U. Level 6 shows how the CORDIC unit gets from the angle to the number.

How CORDIC computes cos

CORDIC is one small engine that computes cos, length (MAG), divide and square root with shifts and adds only. For cos, it starts with the arrow (x, y) = (1, 0) and turns it 16 times, by smaller and smaller fixed angles, until it points at the input angle φ. Step i turns by atan(2^−i): 45°, 26.6°, 14.0°, … This angle is picked because turning by it needs no multiplier. Turning (x, y) by an angle θ gives cos θ × (x − y × tan θ, y + x × tan θ). For θ = atan(2^−i), tan θ = 2^−i, so a multiply by tan θ is a shift by i bits. The unit leaves out the cos θ factor in each step and makes up for all of them once at the end. One step, where both lines use the x and y from before the step:

x ← x − σ × (y ≫ i) y ← y + σ × (x ≫ i) angle left ← angle left − σ × atan(2^−i) σ = +1 if the angle left is ≥ 0 (turn left), −1 if it is below 0 (turn right)

≫ i is a shift right by i bits, which divides by 2^i. For cos, the only table is the 16 turn angles, held in a small ROM inside the CORDIC unit (not the Decode ROM). Leaving out the cos θ factors makes the arrow a little longer at each step; after 16 steps it is 1.64676 times longer, so the unit multiplies x by 1 ÷ 1.64676 = 0.60725 at the end (with shifts and adds) and returns it: x = cos φ. The 16 turns add up to 99.9°, so the input must stay within ±99.8° (docs cordic.md); the matte bounce only uses angles from −90° to +90°.

Baud rates. The clock divider (docs clkdiv.md) makes a clock f = 25 MHz × c ÷ (2 × (b + c)), and the UART needs f = 16 × baud. The docs require b ≥ c and b + c ≤ 127.
115,200 baud: b = 104, c = 18 → 25 MHz × 18 ÷ 244 = 1.844 MHz = 16 × 115,266 baud (0.06 % fast).
230,400 baud: b = 43, c = 18 → 25 MHz × 18 ÷ 122 = 3.689 MHz = 16 × 230,533 baud (0.06 % fast).
Because b ≥ c, the fastest setting is b = c: 25 MHz ÷ 4 = 6.25 MHz = 16 × 390,625 baud. So 460,800 baud is out of reach, and 230,400 is the fastest standard rate. Uploading the scene takes 0.13 s.

Timing COne macro-op, cycle by cycle

The cycle rules. Every count in the table below follows from these rules and the ROM rows (Decode ROM).
1. Cycle 1 (ACCEPT): the Decode Unit takes the request and loads R0–R5.
2. From cycle 2, one micro-op issues per cycle, in ROM order.
3. A micro-op that issues in cycle k on a unit with L cycles is done in cycle k + L. Its result register is written at the end of that cycle.
4. A micro-op with the barrier bit issues only when no micro-op is running: in the cycle after the last done (docs decode.md: the in-flight count must be 0).
5. The CORDIC takes one micro-op at a time: the next CORDIC micro-op issues in the cycle after the CORDIC is done. The ALU and the multiplier take a new micro-op every cycle.
6. After the last done, one cycle sees that nothing runs, and one cycle sends the reply. So a vector macro-op takes (last done) + 2 cycles.
7. A scalar macro-op skips the Register File: 1 accept cycle, the unit’s L cycles and 1 reply cycle, so L + 2.
Unit cycles L: ALU and multiplier 1 (assumed); CORDIC 17 to 23 (Level 6).

ProposalFree compares

Status: open. No cycle count on this page uses it. A compare macro-op (M_LT) costs 3 cycles: accept, ALU, reply. Many compares only ask if a number is below 0, or above or below a fixed constant. Those need no ALU. A negative number in two’s complement has bit 15 (the sign bit) = 1, and the RTU already holds the number (it just came back as a result), so it reads bit 15 directly: a wire, 0 cycles. A compare with a constant is a small gate on the bits. Only compares between two variables (|offset|² < r², t < best t, α_top ≤ det) keep M_LT.
